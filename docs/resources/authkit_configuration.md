# workos_authkit_configuration (Resource)

Manage login callbacks and their default, logout URLs and their default, allowed CORS origins,
the initiate-login URL, signup, and waitlist settings on an existing WorkOS environment and its
default AuthKit application. This resource creates no environments, applications, or customer data.

## Prerequisites and ownership

Account-plane access must be enabled for the owning WorkOS team. Configure the provider with
`account_access_token` (sensitive, or `WORKOS_ACCOUNT_ACCESS_TOKEN`), `account_team_id` (or
`WORKOS_ACCOUNT_TEAM_ID`), and explicit `environment_id` and `application_id`. An account token
does not replace `api_key` for REST resources and must never be used as an application runtime
credential. The API URL remains `base_url`, defaulting to `https://api.workos.com`.

Provider configuration verifies the team, its exact environment, the application's membership and
default status, and `client_id` when configured. If a REST key is supplied, the complete unscoped
role ID sets returned by REST and GraphQL must agree and be nonempty before any resource can run.
Configuration resource targets must match the verified provider target. Missing, stale, or mismatched
targets fail closed; the account API's production fallback is never used as target resolution.

Use **one owner per environment**. All URI/origin sets are authoritative, including removal of
unlisted values. Do not combine this resource with individual `workos_redirect_uri` resources,
another singleton, or another configuration writer for the same environment.

## Example

The example uses existing IDs and credentials supplied separately to the provider:

```terraform
provider "workos" {
  client_id      = var.client_id
  environment_id = var.environment_id
  application_id = var.application_id
}

resource "workos_authkit_configuration" "app" {
  environment_id       = var.environment_id
  application_id       = var.application_id
  redirect_uris        = ["https://app.example.com/callback"]
  default_redirect_uri = "https://app.example.com/callback"
  logout_uris          = ["https://app.example.com/signed-out"]
  default_logout_uri   = "https://app.example.com/signed-out"
  cors_origins         = ["https://app.example.com"]
  initiate_login_uri   = "https://app.example.com/login"
  allow_signup         = true
  waitlist_enabled     = false
}
```

After apply, a refresh reads the selected defaults and complete sets back from WorkOS. A subsequent
plan should show no changes. Existing unrelated AuthKit settings are omitted from mutation inputs
and remain unmanaged.

## Schema

### Required

- `allow_signup` (Boolean) Whether AuthKit allows user signup.
- `application_id` (String) Exact default AuthKit application ID belonging to environment_id. This is the application ID, not its client ID.
- `cors_origins` (Set of String) Complete allowed HTTP(S) web origin set without paths, queries, credentials, wildcards, or fragments. An empty set disables all allowed origins.
- `default_logout_uri` (String) Default logout URL; must be a member of logout_uris.
- `default_redirect_uri` (String) Default callback URL; must be a member of redirect_uris.
- `environment_id` (String) Exact environment ID belonging to account_team_id; checked before every configuration mutation.
- `initiate_login_uri` (String) Absolute HTTP(S) initiate-login URL.
- `logout_uris` (Set of String) Complete set of absolute HTTP(S) logout URLs. Replaces the full remote set.
- `redirect_uris` (Set of String) Complete set of absolute HTTP(S) callback URLs. Replaces the full remote set. Do not combine with workos_redirect_uri for this application.
- `waitlist_enabled` (Boolean) Whether AuthKit enables the signup waitlist.

### Read-Only

- `id` (String) Singleton import ID: environment_id/application_id.

URLs must be absolute HTTP(S) URLs without credentials, wildcards, or fragments. Origins must
have no path, query, or trailing slash. HTTP supports local development; use HTTPS for public
origins. This resource deliberately supports explicit web URLs rather than WorkOS wildcard or
custom-scheme URL features.

Changing the provider target requires explicitly detaching the old singleton first, then updating
the provider and resource targets together. A resource cannot refresh a target different from its
verified provider target.

## Import and destroy

Import attaches Terraform to existing configuration without a mutation:

```shell
terraform import workos_authkit_configuration.app environment_01EXAMPLE/application_01EXAMPLE
```

Review the resulting plan before applying: the first apply will remove remote entries missing
from the configured sets. Existing roles can be imported separately with
`terraform import workos_environment_role.viewer viewer`.

**Destroy only detaches this resource from Terraform state.** The provider emits a warning and
leaves every remote setting unchanged. There is no remote singleton deletion or reset operation.
Import the same ID to resume management. No environment, application, or customer data is deleted.

## Failures and recovery

Every intended value is validated locally before mutation. The server then dry-runs all changed
URI/origin lists before any persistent write. Team/environment/application ownership is checked
again before each write. URI and logout reads use the application's complete array fields rather
than capped list queries; incomplete or oversized responses are rejected.

WorkOS does not offer an atomic transaction across these settings. After each write the provider
reads back configuration. If a later write fails, available observed state is retained, the error is
reported, and another apply reconciles remaining differences. A transport failure can leave an
uncertain write outcome; refresh and retry. Terraform may mark a failed initial creation as tainted;
replacement is safe because singleton destroy only detaches and never resets the remote settings.
An expired token or HTTP 403 requires a current account credential or restored account-plane/team
access. Raw server messages and response bodies are not included in configuration diagnostics.

## API evidence and live verification gate

The native client uses the official WorkOS CLI's
[GraphQL catalog](https://github.com/workos/cli/blob/main/src/catalog/mcp-catalog.snapshot.json),
[account bearer transport](https://github.com/workos/cli/blob/main/src/lib/dashboard-graphql.ts), and
[target validation](https://github.com/workos/cli/blob/main/src/lib/environment-target.ts).
It uses `setRedirectUris`, `setLogoutUris`, `setWebOrigins`, `updateUserlandApplication`, and
`updateUserlandSettings`; no CLI subprocesses, browser cookies, or guessed REST endpoints are used.

HTTP mocks and Terraform lifecycle tests verify local request/state behavior. Live account-plane
capability has **not** been verified: development had no WorkOS test environment or credentials.
Before using a real account, require a disposable WorkOS test environment, an enabled team feature
flag, exact environment/application/team IDs, and both credentials when managing REST roles.
Verify import/refresh, apply, defaults and full-set readback, a second no-op plan, drift correction,
and detach behavior there. Mock success is not evidence of a successful live WorkOS apply.
